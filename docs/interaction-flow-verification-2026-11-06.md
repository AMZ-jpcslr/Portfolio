## 1. まにあう

根拠: `train_time/src/main.tsx`, `App.tsx`, `StationPicker.tsx`, `railway/RailWalkingSetup.tsx`, `paper/TicketBoard.tsx:10-33`, `paper/model.ts`, `domain/journey.ts`。

- 現行mainは通常 `paper=true, railway=true`。紙の切符風カードが標準。前日の別画面の文言と混在させない。
- 最小フロー: 位置取得操作 → 駅検索と候補選択 → 対象入口への徒歩経路が確定 → 各便の判定が更新 → 便カードの「＋」を押す → 同じカード内で詳細が展開。
- 標準見出しは「次の電車、まにあう？」、詳細は「ここにいられる目安」「出る目安」「徒歩…分 ＋ 駅構内・余裕…分」。詳細は別ページやモーダルではない。
- 判定表示: `余裕あり` / `急げば間に合う` / `現在地から間に合わない` / `現在地からの判定は未確認`。過去便は「発車時刻を過ぎました」。
- 09:04、徒歩5分、駅構内・余裕3分の合成条件なら09:10便は間に合わない、09:15便は余裕3分、出る目安09:07。計算は一致する。時刻表からの引用と扱わない。
- 位置取得だけでは判定できない。新鮮な座標、入口、徒歩経路、現行確認済み時刻表が揃う成功例として描く。駅を変更した時は前駅の徒歩結果を引き継いで即確定しない。
- 地図表示、停車駅列、到着時刻、リアルタイム遅延、乗車完了はこの最小フローに追加しない。実装の便詳細は出発目安・徒歩条件、データがあれば番線・両数。

## 2. しゅうかつ手帳 v2

根拠: [固定コミットのimport-inbox.tsx](https://raw.githubusercontent.com/AMZ-jpcslr/Syukatu-Note/1b7edbe1e1c02be1c615ff2ce559fdcabf1d4ba1/src/components/import-inbox.tsx)、[import.spec.ts](https://raw.githubusercontent.com/AMZ-jpcslr/Syukatu-Note/1b7edbe1e1c02be1c615ff2ce559fdcabf1d4ba1/tests/e2e/import.spec.ts)、前日確認doc。

- 最小フロー: 通知テキスト貼付 → 端末解析 → 保存前の候補確認 → Inbox保存 → 確認待ち項目の反映先・企業名・卒年度・日程と証拠を確認 → 承認 → タスク/カレンダーを確認。
- ボタンの順序は「この端末で解析する」→「この抽出結果をInboxに保存」→「確認して反映」。解析直後にタスクや予定を出現させない。
- **企業名と卒年度は承認前の必須条件**。合成入力例に `サンプル社 2028卒` を含め、承認候補で卒年度2028を確認できるようにする。欠けると正常成功のフローにならない。
- 日程の選択、タスク作成、カレンダー追加は既定で選択済み。未チェックから選択したければ、先に外す操作が必要。最小映像ではチェック済みを確認して承認する。
- 日時未確認の候補はカレンダーに入らない。年が明記された締切例を使う。
- 本番DB保存の成功やGmail自動受信は今回の検証対象外。保存と承認の成功状態を、実装に基づく合成デモとして再現する。
- 2026年11月の月曜始まりカレンダーは11/1が日曜、11/12が木曜。手書き日付グリッドでここをずらさない。

## 3. Streaming Screen

根拠: `studio/editor.html`, `editor.js:10-18,140-145,219-234,309-360`, `schema.js:67-95`, `render.js`。

- `/studio` の「T  表題」をクリックすると、新規モジュールは名前「表題」、表示文字「今日の配信タイトル」で追加。空欄ではない。
- 選択したモジュールの「表示テキスト」に例文を入力 → キャンバス上でドラッグ → 「保存して配信に反映」を押す → 「配信画面 ↗」の `/overlay` を開く。
- 編集中の保存ボタンには `●` が付き、成功表示は「保存しました。OBSには約2秒以内に反映されます」。これは実装の文言であり、今回OBSへの実反映を測った結果ではない。
- titleの背景は既定 `transparent`。overlayで編集用ハンドルや選択枠を表示しない。色付き帯を描くなら、背景パネル等の既存要素として整合させる。
- 編集設定は右側の「モジュール設定」。下部フォームへ大きく移す場合は画面の完全再現ではなく簡略再現として扱う。
- 保存前に配信側が更新されたようには描かない。配信開始、OBS接続、YouTube送信はこの操作だけでは実行されない。

## 4. Yomiage Bot

根拠: `src/commands/voice_web.ts:145-187`, `src/voice_web_api.ts:465-470,546-560` とキュー処理。

- ユーザーがVC「通話」に入る → サーバーのテキストチャンネル「テキスト」で `/voice_web join` → Botも同じVCへ入る → 同じテキストチャンネルに投稿 → 音声生成キュー → BotのVC発話リング。
- join成功は公開応答（ephemeralではない）。返答は次のテンプレート。チャンネル名を映像の表示と一致させる。

```text
🎤 ボイスチャンネルに参加しました！
📻 接続先: 通話
📝 読み上げチャンネル: テキスト

✅ APIキーが設定されています。

🎯 このチャンネルでメッセージを送信すると読み上げられます。
⚙️ 音声設定を変更するには /voice_web settings を使用してください。
```

- Engine設定の場合はAPIキー行の代わりに「✅ VOICEVOX Engine 接続先が設定されています。」。映像で実資格情報を出さず、設定済み成功例として使用。
- ユーザーが先にVCへ入っていない場合は「❌ ボイスチャンネルに参加してからコマンドを実行してください。」となる。
- Botの投稿と別チャンネルの投稿は対象外。翻訳を音声生成の前段へ混ぜない。
- 発話リングはDiscordクライアントの音声再生状態の再現。プロジェクトに独自の「読み上げ完了」カードがあるようには描かない。

## 5. Shindo Bot

根拠: `src/commands/set_eq_channel.ts`, `set_eq_threshold.ts`, `eq_notify.ts:556-570`。

- 管理者が `/set_eq_channel channel:#地震速報` → `/set_eq_threshold threshold:3` → 新しい条件適合情報が到着 → 指定チャンネルに通知。設定コマンド自体は地震通知を発火しない。
- channel成功: 「地震・津波情報の通知先を #地震速報 に設定しました。」
- threshold成功: 「地震通知を「震度3以上」に設定しました。」
- **設定応答は両方ephemeral**。本人だけに表示される体裁にする。サーバー全員へ投稿された通常メッセージとして扱わない。
- 最低震度は選択値文字列 `3`、表示ラベルは「震度3以上」。管理権限とBotの通知権限が揃う成功例。
- P2Pの通常地震情報の最小通知: content「地震情報: サンプル県沖 最大震度 3」、青 `#2d6cdf` のembed、タイトル「地震情報」。項目は「震源」「規模」「深さ」「最大震度」「発生時刻」「津波」。例: サンプル県沖 / M4.1 / 30km / 3 / 架空日時 / 心配なし。
- footerは `Source: P2P地震情報 / 気象庁` が既定。地図・観測点は条件付き。必須でないので最小再現では省略可。
- 黄色の警告風カード、赤い緊急地震速報と通常地震情報の混同を避ける。架空地震注記は動画外に置く。

## 6. Artificial Moral Architecture

根拠: `examples/demo.py`, `docs/assets/cli-demo.txt`。今回は実行せず、前日実行済み記録と保存出力を照合。

最小操作は端末で `python examples/demo.py` を入力しEnter。A→B→C→D→Eの順に出力される。Bだけ取り出すなら端末スクロール/切り取りとして描き、架空のB選択GUIを作らない。

```text
[B_information] ユーザーに必要な情報を提供する
  Decision: MODIFY
  private: BLOCK (utility=0.95, uncertainty=0.15)
  private:alternative:use_public_information: ALLOW (utility=0.75, uncertainty=0.15)
  private:alternative:request_permission: ALLOW (utility=0.5, uncertainty=0.15)
  Selected: private:alternative:use_public_information
  Execution: simulated
```

初稿の `cliLines` は保存済みA〜E出力と一致。長い行は折返し又は読めるサイズを維持する。数値は合成シナリオのutilityで、性能評価値ではない。実CLIの色付き出力は未確認なので、正確な端末再現を優先するなら単色文字が確実。

## 7. Inspection Proxy

根拠: `src/inspection.js`, `pii.js`, `dashboard/render.js:64-70,565-578`。

- 合成HTTP通信 → HTTP 200が返る → 転送後のPII候補件数が記録 → 管理画面の該当行 →「詳細」リンク。
- HTTPステータスをcurl端末に表示する例なら `curl -i -x 127.0.0.1:8080 http://127.0.0.1:8088/sample`。`-i`無しでヘッダーが当然表示される描写にしない。架空サーバーのアドレスと応答として外側で明示する。
- 一覧の文言は `PII(メール) 転送後通知 (1)` とリンク「詳細」。`PIIのみ` フィルタと「適用」は実在。
- **詳細はモーダルではなく `/entry/{id}/pii` の別ページ**。最小実画面:

```text
戻る
PII 通知
転送後の通知です。漏えいの遮断を意味しません。本文や一致サンプルは保存・表示しません。
要求: {検査状態} / 応答: {検査状態}
• メール: 検出 (件数=1)
• カード: 保存された検査範囲で未検出 (件数=0)
• 電話番号: 保存された検査範囲で未検出 (件数=0)
```

- メールの原文・マスクしたサンプルも表示しない。「PII検知→通信ブロック」「漏えい阻止」は不可。転送とPII通知を時間順に見せる。
- 要求/応答の検査状態は合成レスポンスの内容・上限と整合させる。実PII検出器を通した値を今回得たわけではないので、固定1件は合成例。

- 合成軌道でよいが、実シミュレーション録画、実機試合、成功率評価とは扱わない。
